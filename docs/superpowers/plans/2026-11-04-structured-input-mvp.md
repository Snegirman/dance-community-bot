# План реализации бота с вводом по шаблону

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> or superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.
> Правила проекта задают способ исполнения: код и тесты пишет `luna_worker`,
> главный агент проводит ревью, исправляет ошибки и проверяет исправления.

**Цель:** владелец сохраняет события и регулярные занятия по шаблону, управляет
отменами/переносами и получает проверяемую недельную публикацию без нейросети.

**Архитектура:** один Python-процесс с aiogram и aiohttp webhook; SQLite и оригиналы
афиш на постоянном диске. Проверка полей и расчёт расписания отделены от Telegram.
Публикация использует сохранённый снимок и журнал частей выпуска.
По запросу владельца 05.11.2026 транспорт переведён на webhook;
подробности в [отдельном плане перехода](2026-11-05-webhook.md).

**Стек:** Python 3.13, uv, aiogram 3, aiohttp, Pydantic 2, стандартные `sqlite3`,
`asyncio`, `zoneinfo`, pytest и Ruff. Файловые/SQLite-операции выполняются через
`asyncio.to_thread`, транзакция целиком внутри одного вызова. Новые зависимости
для этого плана не требуются; изменения зависимостей потребуют обновления `uv.lock`.

**Спецификация:** [согласована владельцем 04.11.2026](../specs/2026-11-04-structured-input-design.md).
Правила работы: [AGENTS.md](../../../AGENTS.md). Этот план заменяет
[архивный план с OpenAI](2026-11-04-bot-mvp.md).

**Состояние:** план утверждён владельцем 04.11.2026; задача 1 выполнена
и проверена 04.11.2026, задачи 2–9 не начаты. По указанию владельца выполняем
задачи поэтапно: начинаем выбранную задачу только по его отдельной команде
и не переходим к следующей автоматически.
Повторное согласование спецификации и плана не требуется.

## Общие ограничения

- Только Python 3.13, локальная `.venv` и uv; общение и сообщения владельцу на русском,
  идентификаторы на английском. Аннотации без `typing.cast` и необоснованного `Any`.
- Без OpenAI, других нейросетей, OCR, поиска событий и веб-интерфейса.
- Одно сообщение по шаблону — одна запись, не более одной афиши на карточку.
- Разовое событие: обязательны название, дата и тип; остальные поля необязательны.
  Регулярное занятие: обязательны название, первая дата и время; тип «Занятие».
- Форматы `ДД.ММ.ГГГГ` и `ЧЧ:ММ`, зона `Europe/Moscow`. Неизвестная цена
  не равна бесплатному участию; неизвестное время не равно полуночи.
- Сначала источник в базе, затем проверка; до подтверждения запись — черновик.
  Исходники, афиши и история не исчезают при отмене или правке.
- Неделя: `[понедельник 00:00, следующий понедельник 00:00)` по Москве.
  Исключение связано с ID серии и исходной датой, даже после нескольких переносов.
- Любое административное сообщение/callback требует ID владельца и личного чата.
- Один выпуск на пару «группа, начало недели». Неизвестный результат отправки
  требует решения владельца. Изменения опубликованного поста владелец сообщает вручную.
- Автотесты не используют реальные ключи, сеть и личные материалы. Данные,
  секреты и резервные копии исключены из Git.

## На что обратить внимание при ревью

1. Повтор доставки после сбоя между сохранением источника и черновика должен
   продолжить обработку; уникальность источника не должна навсегда блокировать запись. Тест задачи 2.
2. Перезапуск между скачиванием файла и фиксацией пути в базе не должен давать
   активную карточку с потерянной афишей. Тест задачи 3.
3. Сохранение перенесённого проведения отдельным событием перед изменением серии
   не должно на промежуточном шаге дублировать занятие в публикации. Тест задачи 4.
4. Длинные тарифы, emoji, HTML-символы и предельные даты не должны теряться
   при разбиении поста или вызывать переполнение даты. Тесты задач 1 и 5.
5. Поддельный/устаревший callback и ответ на карточку после перезапуска не должны
   изменять другую запись; разрешение неизвестной доставки не должно слепо
   возобновлять весь выпуск. Тесты задач 3, 6 и 8.

## Исходное состояние и порядок

Реализованы запуск, настройки Telegram, `/start`, `/help` и общий барьер доступа.
База, ввод, расписание и публикация отсутствуют. Предыдущие результаты тестов
описаны в архивном плане; перед реализацией нужен новый исходный прогон.
В рабочей папке уже есть незакоммиченные изменения первого этапа и документации.
Не отменять их и не включать чужие изменения в коммиты автоматически.

Задачи выполняются последовательно: 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9.
После задачи 3 можно проверить полный путь разового события до базы,
после задачи 4 — расписание, после задачи 6 — ручную публикацию.
Живые проверки и сервер отмечаются отдельно и не блокируют автономные задачи.

Перед первым запуском Python настроить инструменты на локальную `.venv`.
Исходные команды: `uv sync --locked`, `uv run pytest -q`,
`uv run ruff check .`, `uv run ruff format --check .`.
Для нового прикладного сценария сначала увидеть ожидаемый провал теста,
затем реализовать минимальный код и получить успех. Тестовые файлы ниже
появляются в соответствующих задачах. Асинхронные тесты используют `asyncio.run`.

Проверка каждого этапа: целевые тесты, обе команды Ruff, ревью главного агента,
обновление README и отметок плана. Коммит, если он создаётся, содержит только
проверенные изменения этапа; незавершённые пункты остаются незавершёнными.
