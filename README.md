# Dance Community Bot

Telegram-бот для танцевальной беседы: каждую неделю публикует расписание занятий
и события, которые владелец заранее ввёл по шаблону и подтвердил. Направления
занятий — Popping, Animation и Waving. Регулярные занятия учитывают отмены
и переносы на отдельные даты. Нейросеть и поиск событий в интернете не используются.

04.11.2026 владелец выбрал ввод по шаблону вместо распознавания материалов.
Подробные правила собраны в [согласованной спецификации](docs/superpowers/specs/2026-11-04-structured-input-design.md).
Владелец подтвердил её 04.11.2026. Приём сообщений по шаблону в Telegram
и публикации пока являются требованиями; типы данных, проверка шаблонов
и хранилище SQLite реализованы отдельно от обработчиков.

## Текущее состояние

Реализован код первого этапа — запуск Telegram-бота и доступ владельца:

- приём webhook через aiogram 3 и aiohttp, регистрация адреса при запуске;
- загрузка и проверка токена, числового ID владельца и настроек webhook
  из окружения или `.env`;
- проверка секретного заголовка Telegram до передачи сообщения обработчикам;
- команды `/start` и `/help`, доступные владельцу в личном чате;
- общая проверка доступа для сообщений и callback-кнопок;
- автономные тесты настроек, авторизации и закрытия ресурсов.

Также реализована задача 1 нового плана — типы и проверка шаблонов:

- модели разового события и регулярного занятия с проверкой обязательных полей
  и диапазонов дат, в том числе при загрузке сериализованных данных;
- разбор полей, строгие форматы дат и времени, русские сообщения об ошибках;
- сохранение неизвестных значений и многострочных тарифов без подстановок;
- предупреждение о прошедшем начале по явно переданному времени в московской зоне.

Также реализована задача 2 — хранилище SQLite:

- исходные сообщения с защитой от повторной доставки и возможностью продолжить
  обработку после сбоя между сохранением источника и созданием черновика;
- черновики, подтверждённые записи и история версий и источников;
- проверка ревизий при подтверждении, отклонении и отмене; старый черновик
  не восстанавливает отменённую запись, повтор подтверждения не меняет её снова;
- транзакции в отдельном потоке, миграция базы и проверка данных при чтении.

Приём шаблонов через Telegram, подключение хранилища к обработчикам,
управление расписанием и публикации ещё не реализованы.
Команды `/event` и `/class` пока недоступны.
Живая проверка Telegram пока не выполнена: нужны реальные
настройки и доступный Telegram HTTPS-адрес. Автоматические проверки работают
без реальных ключей и обращений к Telegram.

## Быстрый старт

Используем Python 3.13 и [uv](https://docs.astral.sh/uv/getting-started/installation/).
Версия Python задана в [.python-version](.python-version), зависимости и инструменты —
в [pyproject.toml](pyproject.toml). Точные версии зависимостей закреплены
в [uv.lock](uv.lock); этот файл хранится в Git.

Если uv установлен локально в `.tools/uv`, добавь его в PATH текущего терминала:

```bash
export PATH="$PWD/.tools:$PATH"
```

Из корня проекта:

```bash
uv sync
cp .env.example .env
```

`uv sync` создаст локальное окружение `.venv` и установит пакет и инструменты
разработки. При отсутствии подходящего Python uv может скачать его; для первой
установки нужен интернет. Системный Python менять не требуется.

В `.env` заполни обязательные параметры локально:

| Переменная | Значение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Токен от BotFather |
| `TELEGRAM_OWNER_ID` | Положительный числовой ID владельца, не username |
| `TELEGRAM_WEBHOOK_URL` | Полный публичный HTTPS-адрес обработчика, например `https://bot.example.com/telegram/webhook` |
| `TELEGRAM_WEBHOOK_SECRET` | Отдельный секрет: 1–256 символов `A–Z`, `a–z`, `0–9`, `_`, `-` |

Секрет можно сгенерировать локально командой `openssl rand -hex 32`.
Он используется для заголовка `X-Telegram-Bot-Api-Secret-Token`,
который Telegram добавляет к запросам. Токен бота в URL не нужен.
URL не должен содержать логин, пароль, query-параметры или фрагмент.

Необязательный `WEBHOOK_PORT` задаёт локальный HTTP-порт (по умолчанию 8080).
Бот слушает только `127.0.0.1`; HTTPS обеспечивает туннель или reverse proxy.
Путь `DATABASE_PATH` описан ниже в разделе хранилища. Настройки группы и
автопубликации пока не используются и могут оставаться пустыми.
Переменные окружения имеют приоритет над `.env`; файл читается из текущей папки.
Не отправляй реальные токены в переписку и не добавляй их в Git.

Запусти бот из корня проекта:

```bash
uv run dance-community-bot
```

При запуске бот регистрирует webhook и принимает входящие POST от Telegram
на путь из `TELEGRAM_WEBHOOK_URL`. Постоянного опроса Telegram нет.
Накопленные сообщения при регистрации не удаляются.
Для остановки нажми `Ctrl+C`; регистрация webhook при этом сохраняется.
Без обязательных настроек запуск завершается с понятной ошибкой;
значения секретов в ней не выводятся.

Также пакет можно запустить как модуль:

```bash
uv run python -m dance_community_bot
```

Проверки:

```bash
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
```

Для форматирования: `uv run ruff format .`. Тесты используют временные настройки
и тестовый транспорт Telegram, не требуют реальных ключей и не отправляют сообщения.

Шаблон настроек — [.env.example](.env.example). Секреты, база, исходные материалы
и резервные копии исключены из Git.

### Хранилище SQLite

`DATABASE_PATH` задаёт путь к базе, по умолчанию `data/dance-community-bot.sqlite3`
относительно текущей папки. Оригиналы афиш предназначены для папки `posters/`
рядом с базой; отдельной настройки пути к афишам нет.

Хранилище используется через `Store(path)` и `await store.initialize()`.
Инициализация создаёт каталоги и применяет SQL-миграцию; повторный вызов
сохраняет существующие данные. Каждая операция открывает и закрывает своё
соединение, выполняя SQL и транзакцию целиком через `asyncio.to_thread`.
Подключение `Store` к запуску бота и скачивание афиш относятся к задаче 3:
нынешний запуск webhook ещё не сохраняет сообщения в SQLite.

### Локальный webhook через туннель

Публичный IP у компьютера не требуется. Установи
[cloudflared](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)
и запусти в отдельном терминале:

```bash
cloudflared tunnel --url http://127.0.0.1:8080
```

Туннель выдаст адрес вида `https://example.trycloudflare.com`.
Укажи в `.env` полный адрес с путём, например:

```dotenv
TELEGRAM_WEBHOOK_URL=https://example.trycloudflare.com/telegram/webhook
```

После заполнения остальных обязательных настроек запусти
`uv run dance-community-bot`. Оба процесса должны работать одновременно.
При изменении `WEBHOOK_PORT` измени и порт в команде туннеля.
При новом запуске Quick Tunnel адрес меняется: обнови URL и перезапусти бот.
Не включай интерактивную авторизацию туннеля: Telegram должен обращаться
к обработчику напрямую; запросы защищены секретом webhook.

Для разработки используй отдельного тестового бота: у одного токена может быть
один webhook, и локальный запуск с рабочим токеном заменит серверный адрес.

### Webhook на общем сервере

HTTPS-прокси направляет только выбранный путь к боту на `127.0.0.1:8080`.
Например, внутри существующего HTTPS `server` в nginx:

```nginx
location = /telegram/webhook {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
}
```

В `TELEGRAM_WEBHOOK_URL` укажи внешний HTTPS-адрес с тем же путём.
Прокси должен сохранять путь, тело POST и заголовок
`X-Telegram-Bot-Api-Secret-Token`. Сертификат обслуживается прокси;
локальный HTTP-порт бота открывать в интернет не нужно.
Если порт занят другим приложением, выбери свободный `WEBHOOK_PORT`
и обнови адрес `proxy_pass`.
Хостинг, управление процессом и живая серверная проверка ещё не настроены.

### Живая проверка первого этапа

После настройки и запуска отправь боту `/help` без предварительного `/start`,
затем `/start` со своего аккаунта в личном чате. Бот должен описать доступные
команды и ограничения текущего этапа. Обычный текст или фото пока не сохраняются.
Проверь с другого аккаунта и в группе: административные команды должны
игнорироваться. Проверка доступа применяется к каждому сообщению и callback.
Затем останови процесс через `Ctrl+C`.

Результат этой проверки нужно записать отдельно от результатов автотестов.

## Согласованный сценарий первой версии

1. Владелец присылает в личный чат одно событие по шаблону. Афиша необязательна.
2. Бот сохраняет исходное сообщение, проверяет поля и записывает черновик в SQLite.
   При ошибке показывает поле и нужный формат; данные не угадывает.
3. В карточке показывает сведения, неделю или недели проведения и кнопки
   «Сохранить», «Исправить», «Отклонить». Черновик уже в базе; подтверждение
   допускает его к публикации. Повторного подтверждения каждую неделю нет.
4. Регулярное занятие владелец задаёт один раз. Для конкретного проведения
   доступны отмена и перенос, для постоянного изменения — дата начала нового правила.
5. Исправления вносятся полным шаблоном в выбранную карточку. Афишу можно добавить
   ответом на неё; при текстовых правках сохранённая афиша не исчезает.
6. Бот собирает предпросмотр и публикует текущую неделю по понедельникам
   в явно выбранное время. Подтверждённые исключения изменяют конкретные проведения.

Управление доступно только владельцу; участники группы получают публикации.
MVP принимает текст по шаблону и одну фотографию на карточку.
Произвольный текст, альбомы, PDF и голосовые не распознаются. Веб-интерфейс не нужен.

Пример события; необязательные строки можно пропустить:

```text
Название: Popping Jam
Дата: 14.11.2026
Тип: Джем
Время: 18:30
Место: Студия, адрес
Стоимость: 500 ₽; зрителям бесплатно
Описание: Свободные выходы, после — общая практика
```

Обязательны название, дата и тип. Тип — произвольная непустая строка без
классификации; сохраняем регистр, убираем пробелы по краям.
Время и место — дополнительные необязательные поля. Для многодневного события
предусмотрена `Дата окончания`.
Формат регулярного занятия и полная грамматика ввода описаны в спецификации.

## Данные и правила расписания

| Сущность | Основные сведения |
| --- | --- |
| Регулярное занятие | Название, первая дата, время, необязательная последняя дата; день недели определяется по первой дате |
| Исключение из расписания | Серия и исходная дата проведения; отмена либо перенос на новую дату и время |
| Разовое событие | Название, тип, дата; необязательные время, дата окончания, место, стоимость, описание и афиша |

У записей сохраняем исходные сообщения, оригиналы афиш, версии и статус
подтверждения. Конкретное расписание занятий пока не задано.

Правила:

- Дата — `ДД.ММ.ГГГГ`, время — `ЧЧ:ММ`, часовой пояс — `Europe/Moscow`.
  Невозможные/относительные даты и даты без года отклоняем с объяснением.
  Прошедшую дату показываем с предупреждением до подтверждения.
- Отсутствующее время остаётся неизвестным; неизвестная стоимость не означает
  бесплатное участие. Тарифы и условия храним текстом без потери подробностей.
- Неделю вычисляем из даты проведения. Многодневное событие включаем один раз
  в каждую неделю пересечения; последний день события включён.
- Отмена затрагивает одно проведение. Перенос убирает его с исходной даты
  и добавляет на новую, в том числе в другую неделю. Остальная серия сохраняется.
- Повторный перенос меняет то же проведение. Отмена перенесённого занятия
  не возвращает его на исходную дату; для возврата нужно убрать исключение.
- Постоянные изменения действуют с указанной даты. Ранее заданные исключения
  нужно разобрать до изменения затронутой части серии; молча терять их нельзя.
- Бот не проверяет содержимое афиши. Несколько событий с одной афиши владелец
  вводит отдельными карточками и сам проверяет соответствие изображения полям.
- Повтор доставки сообщения и нажатия кнопки не создают копии. Похожие события,
  присланные разными сообщениями, вызывают предупреждение, а не молчаливое слияние.

Подтверждение карточек, дополнительные поля и ограничения ввода
зафиксированы в спецификации. Изменения базы после публикации
не обновляют уже отправленный пост: в MVP бот уведомляет владельца о затронутых
выпусках, а владелец вручную сообщает об изменении в группе.

## Надёжность и эксплуатация — требования к реализации

- Проверять Telegram ID владельца и личный чат во всех административных действиях,
  включая callback-кнопки. Username не использовать для авторизации.
- Поддержать предпросмотр, редактирование и отмену событий.
- Сохранять черновики и сведения о незавершённой загрузке афиш; позволять
  исправить шаблон или повторить загрузку после перезапуска.
- Учитывать отправленные публикации и сообщения, предотвращать повторы при
  перезапуске и повторном срабатывании планировщика, учитывать частичную отправку.
- Использовать часовой пояс `Europe/Moscow`; неделя — с понедельника до следующего
  понедельника, правая граница не включается. Время понедельничного поста ещё не выбрано.
- До включения автопубликации явно задать время и целевую группу.
- Сохранять снимок выпуска перед отправкой. После начала публикации изменения
  базы не должны попадать в оставшиеся части этого снимка.
- При неизвестном результате доставки останавливать автоматические повторы
  и просить владельца проверить чат. Не обещать абсолютное отсутствие дублей
  при потере ответа после возможной отправки.
- Хранить SQLite, исходные материалы и афиши на постоянном диске. Предусмотреть
  согласованные резервные копии базы и файлов, а также проверку восстановления.
- Хранить ключи в окружении, не выводить их и содержимое личных материалов в логи.
